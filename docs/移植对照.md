# 从 sheng（小米平板 6S Pro）移植到 vermeer（红米 K70 / POCO F6 Pro）

本文是这次移植的**依据与账本**：每个 sheng 组件对应到 vermeer 的什么、依据是什么、
哪些照搬、哪些替换、哪些删掉。所有"上游有什么"的结论都来自 2026-10-17 对仓库的实测
（GitHub API / 仓库文件内容），不是推测。

---

## 0. 三句话结论

1. **sheng 项目本身只是"脚手架"**：27 个文件、约 2700 行脚本，
   `Xiaomi-pad-6s-pro-Linux` 那棵树里只有文档；真正能复用的构建逻辑在
   `code002-2/ubuntu-sheng`（GitHub Actions + `scripts/host|in-chroot`），本仓库就是它的 fork。
2. **`k70移植方案.txt` 里"最大工作量"的两件事已经被别人做完了**：vermeer 的设备树与
   面板驱动早在 [Xlie-Electronic-Customs/linux](https://github.com/Xlie-Electronic-Customs/linux)
   里（`sm8550-xiaomi-vermeer.dts` 28,741 B + `drivers/gpu/drm/panel/panel-n11-42-02-0a-dsc.c`），
   固件也在 `linux-firmware-xiaomi-vermeer` 里。**不需要**从零写 DTS、也不需要写面板驱动。
3. 真正必须改的是四个"接口层"的东西：**内核来源与配置合并方式**、**boot.img 头版本**、
   **固件包目录结构**、**设备专属包（传感器/alsa/xiaomi-*）的取舍**；再加上设备形态
   （手机 vs 平板）的 rootfs 配置。这些本仓库已全部改完。

## 1. 组件对照表

| 组件 | sheng 的取值 | vermeer 的取值 | 处理方式 |
|---|---|---|---|
| 构建流水线 | `ubuntu-sheng`（rootfs.yml + _packages.yml + scripts/） | 同结构 | **照搬**，只改设备相关参数 |
| 内核树 | `ianchb/sm8550-mainline` @ `sheng-7.2.6` | `Xlie-Electronic-Customs/linux` @ `master`（7.3.0） | **替换**：实测 ianchb 那个仓库只有 `sheng-*` 分支，`sm8550-xiaomi-vermeer.dts` 返回 404 |
| 内核配置 | 仓库根一份完整的 `sm8550.config` 直接当 `.config` | 树内 `defconfig` + `sm8550.config` + `hardening.config` **片段**合并 | **替换**：该树没有 vermeer 的 defconfig，必须 `merge_config.sh` |
| 设备树 | `sm8550-xiaomi-sheng.dtb` | `sm8550-xiaomi-vermeer.dtb` | 替换名字，驱动随树自带 |
| 面板 / 触控 | sheng 自己的面板 + 手写笔 | `panel-n11-42-02-0a-dsc` + Goodix gt9916（都在树里） | 不用动 |
| 固件仓库 | `ianchb/sheng-firmware`（根目录就是固件根） | `XEC/linux-firmware-xiaomi-vermeer`（固件在 `xiaomi-vermeer/` 子目录） | **替换 + 修正路径**（否则驱动找不到） |
| boot.img 头 | header_version **0** + base/kernel_offset/tags_offset | header_version **4**（GKI），无 offset 字段 | **必须参数化**，照抄 sheng 会 `invalid boot image` |
| 启动镜像产物 | `Image.gz-dtb_sheng`（压缩内核 + DTB） | `kernel-dtb_vermeer`（**未压缩** Image + DTB） | 改名 + **不压缩**：K70 原厂 kernel 是未压缩 Image（实测首字节 `MZ`），见 §6 |
| 预编译内核 | 上游每版 release 带 `boot_sheng_dualboot*.img` | 上游**没有**任何带 boot.img 的 release（只有 7.0-rc6 源码 tag） | prebuilt 降级为可选，默认 `custom_build` |
| 传感器 | `sheng-sensors`（SSC registry + udev） | 无对应物 | **删除**（K70 的 registry 还没人提取）；libssc/iio-sensor-proxy 仍构建，便于以后补 |
| 设备认证 | `sheng-devauth`（qtee） | 无 | **删除** |
| 音频 | `alsa-xiaomi-sheng`（WCD938X UCM2） | 主线 AudioReach 未通 | **删除**（装一份错的路由只会更难查） |
| 额外设备包 | `xiaomi-*`（快充/触控/笔/指纹，按 sheng 硬件写死） | 无 | **删除** |
| rootfs 定位 | `root=PARTLABEL=<分区>` + `x-systemd.growfs` | 相同 | 照搬（注意不是 PARTUUID） |
| 设备形态 | tablet / GridUnit 21 / Landscape | phone / GridUnit 18 / Portrait / `CHASSIS=handset` | 替换 |
| 分区与刷写流程 | TWRP + parted 新建分区 → `fastboot flash boot_b` → `set_active b` | 相同 | 照搬（K70 也是 A/B） |

| # | 原文说法 | 判定 | 依据 |

| 1 | 项目本质是 GitHub Actions 构建脚本集合，调 ianchb/sm8550-mainline + sheng-firmware + mkbootimg | ✅ 成立 | `ubuntu-sheng` 的 rootfs.yml / _packages.yml / scripts 结构 |

| 4 | 面板驱动主线大概率没有，是最大工作量，要做好逐行移植准备 | ❌ 不成立（对这棵树） | `panel-n11-42-02-0a-dsc.c` 已在该树；`sm8550.config` 里 `CONFIG_DRM_PANEL_XIAOMI_N1142020A=y` |

| 6 | 固件包直接 `cp -a` 到 `/usr/lib/firmware` | ❌ 需要修正 | 上游固件在 `xiaomi-vermeer/` 子目录，直接铺会把路径变成 `/usr/lib/firmware/xiaomi-vermeer/ath12k/...`，驱动找不到 |
| 7 | `alsa-xiaomi-sheng` 改成 K70 的 codec | ⚠️ 暂不做 | 主线 AudioReach 连 voice/播放图都还没有设备侧 topology；先删包，别制造假象 |

## 4. 仍需在真机上确认的三件事

1. ~~**boot.img 头参数**~~ —— **已用原厂 boot.img 实测确认：header v4 / pagesize 4096 /
   ramdisk 0 / cmdline 空**（详见 §6）。仓库默认值与此一致，不需要再猜。
2. **分区名 / PARTLABEL**：`root=PARTLABEL=linux` 必须与 TWRP 里 `parted name` 设的一致，
   否则内核找不到根（现象：黑屏 + 无 USB，或反复进 fastboot）。
3. **DTB 的交付路径**：原厂 boot.img 的内核尾部**没有** DTB，说明原厂是靠 `vendor_boot`
   （或 `dtbo` 分区）把设备树交给内核的。主线这边默认把 DTB 拼在内核尾部（`append_dtb=true`），
   这是 pmOS 的常规做法，但**在 vermeer 的 ABL 上尚未实测**。
   要彻底定论，需要你 dump 一份 `vendor_boot.img`（和 `dtbo.img`）——见 §6.3。

| 阶段 | 目标 | 现在能不能做 |
|---|---|---|
| A | 构建产物拿到手（不刷机） | ✅ 直接跑 workflow；`boot.img` 头会在构建里自检 |

| C | 进系统：屏幕/触摸/USB/SSH | 驱动都在树里，属"应该直接可用" |

| E | 4G 数据 | 需要设备树补 `&ipa`（本仓库只做了内核配置与用户态，不够） |
| F | 音频 / 通话 | 属驱动开发（AudioReach voice subgraph），不是配置问题 —— **不要在这上面耗时间** |

SM8550 的音频栈是 AudioReach，`q6voice` 是 msm8916-mainline 专属外挂，搬过来只会编不过或起来后无声。

## 6. 用原厂 boot.img 实测核对（2026-10-17）

样本：`boot.img`（96 MiB，即按分区大小 dump 出来的一份 vermeer 原厂启动镜像）。

### 6.1 实测到的头字段

```
unpack_bootimg:
  boot magic            ANDROID!
  kernel_size           46479872      (44.3 MiB)
  ramdisk size          0
  os version / patch    None / None   (0x0)
  header version        4
  command line args     (空)
```

用本仓库的解析器跑同一份文件，结论一致：

```
$ python3 scripts/host/12-analyze-bootimg.py boot.img
[boot header v4] pagesize=4096
boot_header_version: 4
boot_pagesize: 4096
kernel_size: 46479872  ramdisk_size: 0
```

⇒ 本仓库 workflow 的默认值 `boot_header_version=4 / boot_pagesize=4096` **与真机一致**，
不需要再"实测了才知道"。

### 6.2 两个被这份样本纠正的假设

| 假设 | 实测 | 影响 |
|---|---|---|
| kernel 是 `Image.gz`（照 sheng 的做法 gzip 后打包） | kernel 首字节是 `4d 5a`（`MZ` = arm64 EFI/PE 头），**未压缩 Image** | 构建脚本已改成不 gzip；`11-make-bootimg.sh` 会拒绝 `1f 8b` 开头的内核 |
| DTB 拼在 kernel 尾部（pmOS `append_dtb`） | 在内核区间里搜不到 FDT 魔数 `d00dfeed`，整段 kernel 之后是 0 填充 | 原厂 DTB 不在 boot.img 里；主线是否靠"追加 DTB"启动，需真机验证（见 6.3） |

补一条第二次构建（CI 实测）得到的细节：

* 原厂 kernel 的 `MZ` 来自 **CONFIG_EFI=y**（HyperOS 内核带 EFI stub）；
* XEC 树的 `sm8550.config` **显式把 `CONFIG_EFI=n`**（merge 日志：
  `Value of CONFIG_EFI is redefined ... New value: CONFIG_EFI=n`），
  因此我们编出来的 Image 首字节是 `1f2003d5`（arm64 Image 头里的 NOP 签名）。
* 两者都是合法的"未压缩 Image"，构建脚本对这两种形态都放行，只拒绝 gzip。
  本次实测产物：`kernel-dtb_vermeer` 27 MB，内核版本 `7.3.0-rc6-sm8550+`。

另外验证了 mkbootimg 的调用方式：把原厂 kernel 抽出来、用本仓库的 `mkbootimg`
按 `--header_version 4 --pagesize 4096 --cmdline ""` 重打包，头字段逐项一致
（`header_size=1584`、`os_version=0`、`kernel_size` 相同、`ramdisk=0`）：

```
D:/work/boot.img  size=100663296 kernel=46479872 ramdisk=0 hdr_size=1584 hdr_ver=4
repacked.img      size= 46485504 kernel=46479872 ramdisk=0 hdr_size=1584 hdr_ver=4
```

⇒ 本仓库生成的 boot.img 与原厂**同构**，ABL 解析不会因为头结构被拒。

### 6.3 vendor_boot 实测（2026-10-18）—— DTB 的来源确认了

用原厂 `vendor_boot.img`（96 MiB dump）解析，结果非常明确：

```
[vendor_boot v4] pagesize=4096 header_size=2128
kernel_addr:  0x00008000      ramdisk_addr: 0x01000000   tags_addr: 0x00000100
vendor_ramdisk_size: 26730320 (LZ4 压缩的 Android ramdisk)
dtb_size: 3885971   dtb_addr: 0x1f00000   文件内偏移 0x197f000
ramdisk table: 1 条（type=platform, name 空, board_id 全 0）
bootconfig_size: 113
  androidboot.hardware=qcom
  androidboot.memcg=1
  androidboot.usbcontroller=a600000.dwc3
  androidboot.console=ttyMSM0
vendor_cmdline: video=vfb:640x400,... swinfo.fingerprint=vermeer:13/V816.0.11.0.UNKCNXM:user ... bootconfig
```

⇒ **K70 的 DTB 确实在 vendor_boot 里**（3.7 MB，含 57 条 dtbo entry 的对应关系由 dtbo 分区另行提供）。
只刷 boot.img 的话，ABL 会把**原厂 Android 的设备树**交给主线内核 → 面板/UFS 节点对不上。

为此新增 `scripts/host/13-make-vendor-boot.sh`：以原厂 vendor_boot 为模板、
换掉里面的 DTB，产出两个变体。

**回环验证（实测）**：用原厂 DTB + 原厂 ramdisk 重新打包，产物与原厂文件
前 30,629,888 字节**逐字节相同**（sha1 一致）：

```
stock total 100663296  rebuilt 30629888
first 30629888 bytes identical: True
sha1 stock[:n] = sha1 rebuilt = f5a00d005f09304721b2f37d45376f18aba3454a
```

⇒ 我们的打包参数（页大小/各 load addr/dtb_offset/表项/bootconfig 排布）与原厂完全同构，
换 DTB 只会替换那 3.7 MB 的内容，不会引入结构性风险。

还剩最后一步只能在真机上验证：ABL 是否接受 **vendor_ramdisk 为空** 的 vendor_boot
（`vendor_boot-vermeer-noramdisk.img`）。接受就最理想（内核没有 initramfs，直接
`root=PARTLABEL=` 挂 rootfs）；不接受就退回 `-stockrd` 变体，再用我们自己的
initramfs 接管。
